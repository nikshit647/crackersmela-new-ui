# Recovered production backend audit

Date: 27 September 2026. Status: recovered backend source review and local backend fixes complete. The isolated HTTP backend suite passes 72/72 checks; all 13 candidate PHP files pass PHP 8.3.35 syntax checks. A separate template/analytics harness passes 13 isolated regressions. Production PHP 8.1 compatibility lint and complete browser verification remain pending with the coordinating team.

This report distinguishes the recovered **original production source** in `audit-evidence/production-recovery/source` from the **local release candidate** in `audit-evidence/production-release`. Original line references below refer to the recovered source, not the candidate. No production order/customer collections were fetched, no production uploads or messages were submitted, and no production records were changed during this review workstream. Source establishes the vulnerable paths; it does not establish that anyone has exploited them.

Raw recovered files are private audit evidence and may contain credentials. Do not publish them. This report deliberately omits credential values, customer data and secret configuration contents.

## Architecture established from recovered code

- The public and admin sites use the same browser application and PHP endpoints. Catalog, products/settings, orders and analytics are stored in JSON/NDJSON files in a sibling private data directory.
- `staff-auth.php` implements a real PHP password-hash login and server session. The original order, product, catalog, email and analytics endpoints do **not** consult that session.
- The original order/product/catalog/email/analytics authorization keys exactly match the key shipped in the public `js/app.js:79`. Equality was checked in memory and only booleans were emitted.
- Public order creation, order status updates and notification emails originate in browser requests. The original server accepts browser order amounts and customer fields directly.
- `upload-api.php` writes image files to a public upload directory and optionally invokes `rembg`. Email uses PHP `mail()`. The reviewed endpoints do not use a SQL database.
- `.htaccess` supplies selected SPA routes and the XML sitemap alias. The recovered sitemap combines seed JavaScript product data with stored product overrides.

## Established security findings

| ID | Severity | Original location | Finding and consequence | Minimal correction / candidate direction |
| --- | --- | --- | --- | --- |
| SEC-01 | High | `orders-api.php:64-68` | The default/pull branch returns the complete stored order collection without authentication or ownership checks. These are full order objects, including customer fields. This is established by source; no customer data was retrieved to demonstrate it. | Require a server staff session for the collection. Public reads must be scoped to same-browser saved order IDs or an authenticated customer ID. Never scope access by unverified email. |
| SEC-02 | High | `orders-api.php:50-52,71-118`; `products-api.php:55-56,69-92`; `catalog-api.php:81-93`; `js/app.js:79` | A publicly shipped constant is the sole write authorization. A browser-known key can authorize order replacement/status changes, catalog prices/stock/features, product records, coupons and maintenance settings. There is no staff session or capability enforcement on these paths. | Remove shared-key acceptance. Apply server session authorization and CSRF checks to all staff mutations. Rotate/retire the exposed key; merely changing its value and shipping it again does not solve the issue. The candidate common helper provides this boundary. |
| SEC-03 | High | `orders-api.php:71-98,109-113` | Order writes trust arbitrary client IDs, customers, items, prices, quantities, totals, status, dates and logs. Existing records can be replaced by supplied IDs. There is no canonical catalog recalculation, stock enforcement or customer ownership assignment. | Provide a narrowly validated create action: canonical products/prices/discounts, positive bounded integer quantities, authoritative totals, server-generated order identity and timestamps, explicit ownership, and locked validation/order persistence. Inventory reservation is a separate behavior; this release intentionally preserves manually maintained availability rather than introducing a reservation ledger. Staff status updates must allowlist mutable fields. |
| SEC-04 | High | `upload-api.php:19-76` | Upload requires only POST. Any caller can store files and trigger optional background-removal processing without staff authentication, CSRF or request throttling. MIME and 5 MB checks exist, but no decoded dimension/pixel bound exists. | Require staff session, CSRF, upload rate bounds and bounded raster dimensions; validate actual raster data; retain server-generated names and constrain destinations. Bound or remove synchronous external processing. Confirm public upload directories cannot execute scripts. |
| SEC-05 | High | `email-api.php:144-175`; `js/app.js:876,3818` | Public-key holders can supply any recipient and invented order/status details to send branded confirmation/status emails. The endpoint neither loads a persisted order nor verifies ownership, and has no delivery deduplication or rate bound. | Candidate email endpoint accepts only identity, loads the authoritative stored order, verifies session ownership/staff, requires CSRF, uses canonical status copy, and limits duplicate/failed attempts under a private lock. `CM_DISABLE_MAIL=1` prevents actual delivery in tests. |
| SEC-06 | Medium | `analytics-api.php:177-204`; `js/app.js:2519` | The staff report is protected solely by the same public key. It returns internal revenue/order aggregates, locations and search metrics. The browser also puts the key in the URL, allowing it to enter access logs. | Candidate report uses server staff authentication and a request rate limit; no key is accepted. Browser calls must remove the query credential. |
| SEC-07 | Medium | `staff-auth.php:53-66` | Password verification has no attempt limiter. A correct password establishes a session with no application-level idle/absolute expiry or credential-version invalidation in the original `staffAuthenticated()` check at 43-44. The standalone authentication endpoint therefore does not cure the API authorization failures above. | Candidate helper provides strict cookie-only sessions, CSRF/origin checks, credential-version binding, a 30-minute idle timeout and an 8-hour absolute timeout. Candidate login must use bounded attempts, rotate session ID/token, and preserve generic failure messages. |
| SEC-08 | Low | `.htaccess:1-9` | The recovered per-site configuration contains only rewrites, with no HTTPS redirect or response header policy. Parent's earlier safe HTTP checks observed missing HTTPS enforcement and missing HTML security headers. This file alone cannot establish the entire hosting configuration. | Apply tested HTTPS enforcement and a compatible header policy at the hosting/site boundary. Keep the CSP compatible with the existing app until inline handlers/styles are removed; do not claim a strict CSP that is not enforced. |

No high-confidence SQL injection, server command injection or request-driven path traversal was established in the reviewed files. The `rembg` command uses escaped arguments and generated paths; the confirmed issue is unauthenticated, unbounded processing access, not an established command-injection path. Email template text generally uses HTML escaping. Fixed manifest/sitemap paths are not request-driven path traversal.

## Functional and reliability findings

| ID | Severity | Original location | Cause and consequence | Correction |
| --- | --- | --- | --- | --- |
| BUG-01 | Medium | `catalog-api.php:41-60,83-92`; `products-api.php:35-44,74-91`; `orders-api.php:34-45,77-98` | Lock files are opened but never acquired with `LOCK_EX`. Read/merge/revision validation occurs outside any real lock. Concurrent writes can discard updates, and two product writers can accept the same revision. Atomic rename prevents a partial file but does not prevent lost updates. | Hold a common exclusive lock across read, validation/revision check, merge and atomic write. Concurrent stale product updates must produce a conflict. |
| BUG-02 | Medium | `api/manifest.php:6-8`; `api/upload.php:9-134` | These two alternate endpoints contain missing PHP variable names and invalid expressions. They cannot parse. The current browser uses the separate root upload endpoint; do not describe the malformed alternative as an exploitable working upload path. | Candidate manifest is a valid, bounded, fixed-path JSON reader with `{}` fallback, correct `Cache-Control`, nosniff and GET/HEAD only. Replace the obsolete alternate upload with the secured canonical handler or return a deliberate non-success response. |
| BUG-03 | Medium | `.htaccess:5-7`; `index.html:25,363,366`; `js/app.js:3878-3886` | Clean nested `/product/...` paths serve the SPA with relative stylesheet/script URLs, resolving assets beneath `/product/`. Most clean content paths are not mapped back into the hash router and show the home route. These URLs are advertised by the sitemap and canonicals. | Make local asset and API paths root-relative, map each supported clean route and preserve query parameters, and verify direct navigation/reload locally. Avoid rewriting missing asset paths into HTML. |
| BUG-04 | Low | `sitemap.php:26-36`; `js/app.js:111-128` | Extra products in the sitemap do not apply `productOverrides`, so a later disabled/renamed extra product can retain an incorrect sitemap entry. Base-product slug selection can also diverge from the browser merge rules. | Reuse equivalent merge/disabled/slug rules, deduplicate final URLs, and test added/edited/disabled products with controlled fixtures. |
| BUG-05 | Medium | `analytics-api.php:65-68,110-125,149-158` | Events are stored by receipt date but reports select files by occurrence-date range without filtering events by actual occurrence date. Valid events can arrive two days late. Reports can omit those events or include events outside the selected period. | Candidate scans the necessary two-day receipt tail and filters yielded records to the requested occurrence dates. |
| BUG-06 | Medium | `analytics-api.php:110-125,181-204` | A report loads every selected NDJSON event into memory; the allowed inclusive range can cover 91 days, with up to 5 MB/day of raw data before PHP object overhead. There is no report request limit. | Candidate streams records, enforces at most 90 inclusive days and a 16 MiB scanned-data cap with a useful shorter-range response, and limits report requests. These are bounded-design changes; no production performance measurement was taken. |
| BUG-07 | Low | `email-api.php:64,166-170` | Confirmation date uses send time rather than stored order time. Status label/note are escaped before entering a template that escapes them again, displaying entities such as `&amp;` literally. | Candidate uses `placedAt` and canonical raw status labels/notes, escaping only at the HTML sink. |
| BUG-08 | Medium | `js/app.js:874-876` | Original checkout sends confirmation concurrently with order persistence. The secured email endpoint must refuse orders that have not yet been saved, so leaving this sequence unchanged would lose confirmation emails. | Browser integration must await successful canonical order persistence, then request the notification with the saved identity and CSRF token. |
| BUG-09 | Medium | `catalog-api.php:46-49,71-88`; `products-api.php:59-87` | Original mutation schemas accept arbitrary map values and large bodies; malformed numeric values can invalidate prices/stock and arbitrary product/settings fields can break rendering. | Candidate must bound body/map sizes, validate known IDs, finite nonnegative prices, bounded integer stock, booleans and allowlisted product/settings fields. Reject unsupported shapes before persistence. |

## Candidate files implemented by this review workstream

- `audit-evidence/production-release/email-api.php`: server-authoritative stored-order notifications accepting validated `id`, `orderId`, `code`, or legacy `order.id`; same-browser order ownership or authenticated customer ID or staff; CSRF; status updates restricted to staff; separate public (12/hour) and verified staff (120/hour) per-IP request bounds; private per-order/type/status delivery records with a three-attempt limit; a mail-disable switch for tests; safe subject text and useful errors.
- `audit-evidence/production-release/analytics-api.php`: server staff report authorization; same-origin public event POST; bounded body, request/event counts and valid event IDs; UTF-8-safe truncation; private-file modes; streaming, occurrence-date-correct reporting and report bounds.
- `audit-evidence/production-release/api/manifest.php`: valid read-only JSON endpoint with a fixed expected public image-map path and safe empty fallback.
- `cm-security.php`: host-only Secure/HttpOnly/SameSite cookies; strict cookie-only sessions; CSRF and origin checks; staff password-hash configuration/version binding; per-request staff and customer expiry; private atomic JSON writes and full exclusive locks; bounded server rate limits. Identity changes/expiry clear remembered order access and rotate guest retry capabilities.
- `staff-auth.php`: preserves the existing private password-hash configuration, adds environment overrides for fixtures, bounded login attempts, rotating sessions/CSRF, and mutually exclusive customer/staff identity.
- `cm-commerce.php`, `products-api.php`, `catalog-api.php`: bounded product/settings schemas, canonical product merge rules, numeric/boolean/ID checks, safe image and slug rules, full transaction lock scope and optimistic revision checks. Extra products retain their server-assigned extra-product marker.
- `orders-api.php`: server-generated identity/time/status/log, canonical prices and coupons, positive integer quantity/current-stock caps, staff-only POS discounts, idempotent creates, no record replacement, browser/customer-ID ownership, rate-limited code-and-phone lookup, and authoritative staff status updates. Internal identity/retry fields are stripped from public responses.
- `upload-api.php`, `api/upload.php`, `uploads/.htaccess`: staff and CSRF enforcement on both routes; bounded actual raster uploads; decode/re-encode; random filenames; no command execution; upload script execution deny rules. The legacy form field remains supported.
- `sitemap.php`: consistent extra-product overrides, disabled-product filtering, deduplicated URLs, BOM-tolerant seed parsing and isolated data-path support.
- `customer-auth.php` is supplied by the coordinated account workstream. It provides hashed-password customer registration/login, fixed-project server-side Google verification, customer sessions and staff-only user listing. The backend integration suite verifies its order-access contracts. Historical browser-only accounts are not silently migrated or treated as verified identities.

## Required verification before release

The coordinating backend suite records **72/72 PASS** in `audit/backend-security-test-results.json`, with no PHP diagnostics reported by the test owner. These are local fixture tests, not production exploitation. PHP 8.3.35 syntax checks pass for all 13 current candidate PHP files. The 72 HTTP assertions include anonymous and real customer privilege denial, CSRF/origin checks, canonical order tamper protection, retry conflicts, guest and cross-browser customer ownership, expiry/logout revocation, staff updates, POS, notification identity aliases, revision checks, image validation and both upload routes. No PHP warnings, notices or fatal errors were observed in the final isolated run. The local-only `audit-evidence/secondary-tests/templates-and-analytics.php` harness passes 13 checks covering receipt/status escaping and wording, stored order dates, UTF-8-safe event strings, event validation, delayed-event attribution, exclusion of out-of-range events, and absence of request-driven log deletion. These checks use isolated fixtures and disable mail. Production PHP 8.1 compatibility lint, full browser smoke tests and integration checks of the latest frontend call shapes are still in progress; these limited passes are not a production security PASS.

1. Lint every candidate PHP file with the selected portable runtime and verify the runtime matches production capabilities.
2. Use isolated local data and sessions. Anonymous and customer sessions must fail staff catalog/product/report/upload/status operations, including requests containing the retired public key.
3. Prove order A cannot be read, changed or mailed from order B's browser/customer session. Test both same-browser guest access and durable customer ID ownership; an email match alone must not grant access.
4. Prove price/quantity/discount/status/log/identity tampering cannot override canonical order creation. Exercise requested quantities above the stored availability and concurrent writes using fixtures. The candidate checks stored availability but does not decrement/reserve stock when an order is created; this preserves the existing manual inventory semantics and does not guarantee against overselling across distinct orders.
5. With mail disabled or a fake local transport, prove body recipients/content are ignored, duplicate notifications are suppressed, failed delivery attempts are bounded, and no production mail is sent.
6. Verify analytics accepts valid same-origin bounded events, rejects cross-origin/oversized/malformed input, deduplicates event IDs, correctly attributes a delayed event, and rejects overly large report ranges.
7. Verify manifest GET/HEAD response type, valid-map output, missing/invalid-map `{}` fallback, POST rejection, and absence of filesystem path disclosure.
8. Smoke-test direct clean product/content URLs, admin login/logout, canonical order creation, order history, staff CRUD, upload and notification sequencing with the complete candidate.

Analytics requests no longer delete old log files; retention is left to an explicitly authorized maintenance operation. Production configuration and private data remain unchanged by this workstream. Backend exploitation was not attempted on the live application.
